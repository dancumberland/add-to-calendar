## Objectives
- Investigate the new payload format Kit is sending
- Add support for it without breaking existing v1 format

## Implementation Details

### New Kit v2 Format
Kit changed from a complex multi-field format to a clean modern format:

**V1 (legacy)**: `date` + `start_time` + `start_ampm` + `end_time` + `end_ampm` + `tz` (Rails ActiveSupport names)
**V2 (April 2026)**: `start` (ISO local datetime) + `duration` (minutes) + `timezone` (IANA names)

### Changes Made
1. **Format detection**: `isV2Format = !!(startISO && durationMinutes && timezoneIANA)` — if all three v2 fields present, use v2 path. Otherwise fall through to v1.
2. **V2 parsing**: Much simpler than v1 — `DateTime.fromISO(start, { zone: timezone })` gives the start, `.plus({ minutes: duration })` gives the end. No Mode A/B/C complexity.
3. **Placeholder check**: Updated to show placeholder only when BOTH formats are incomplete (not just v1 fields).
4. **Corpus log**: Tags each request as `format: "v2"` or `"v1"` for monitoring the transition.
5. **Bug fix**: `location=undefined` in Google Calendar URLs when location omitted — changed to `location || ""`.

### Variable Scoping Fix
Initial implementation had a scoping bug: `isDateOnly` and `isMidnightUTC` were `const` declared inside the v1 `else` block but referenced in the corpus log section. Fixed by hoisting to `let` declarations at the handler level.

## Key Decisions
- **Dual format support**: Keep v1 fully intact rather than migrating. Existing calendar blocks in published emails still use v1 — breaking those would be worse than maintaining both paths.
- **No timezone mapping for v2**: Kit now sends IANA names directly (`America/Chicago` instead of `Eastern Time (US & Canada)`), so the 134-entry Rails mapping table is only needed for v1.
- **Watch list**: V2 payloads omit styling fields (`background_color`, etc.) when not set. Need to monitor whether Kit sends them when users customize, or if they're gone entirely.
