Fixed the weekly Slack report to compare full completed weeks instead of partial current week vs last week (which produced a fake -67% decline). - `utils/analytics.js` — `aggregateWeeklyData()` accepts `{ force: true }` to overwrite existing aggregates

## Context
Dan received the weekly Slack report on Tuesday at 9:42 AM — it was supposed to fire only on Fridays (cron: `0 19 * * 5`). The report showed a -67% WoW decline (78 vs 239), but this was artificial: it was comparing the current partial week (2 days, Mon-Tue) against the previous full week (7 days). Dan also noticed historical weekly numbers were still missing weekend data from the pre-April-5 aggregation bug.

## Objectives
1. Fix WoW comparison to only compare full completed weeks
2. Backfill historical weekly aggregates to include weekend data
3. Figure out why the report triggered on Tuesday instead of Friday
4. Prevent spurious triggers going forward

## Implementation Details

### 1. Full-Week Comparisons
In `generateWeeklyReport()`, changed the logic to strip the current partial week from trend data before computing stats:
- "This week" = last completed Mon-Sun period
- "Last week" = the one before that
- Chart shows 8 completed weeks only (no misleading partial bar)
- Period dates come from actual week boundaries

### 2. Backfill Route
Added `GET /api/weekly-report?backfill=true&secret=...&weeks=N`:
- Re-aggregates N weeks (max 8) from daily data
- Uses new `force` parameter on `aggregateWeeklyData()` to overwrite stale aggregates
- Daily data has 30-day TTL, so backfill reach is limited

Ran backfill for 4 weeks — significant weekend undercounts found:
| Week | Old | Backfilled | Gap |
|------|-----|-----------|-----|
| 04/05 | 239 | 396 | +157 |
| 03/29 | 395 | 460 | +65 |
| 03/22 | 293 | 350 | +57 |
| 03/15 | 317 | 340 | +23 |

### 3. GET Handler Authentication
Root cause of Tuesday trigger: the GET handler checked that `WEEKLY_REPORT_SECRET` env var existed but never verified it against the request. Any GET request (crawler, bot, uptime monitor) would fire a full Slack report.

Fix: GET handler now requires either:
- Vercel cron: `Authorization: Bearer <CRON_SECRET>` header
- Manual: `?secret=<WEEKLY_REPORT_SECRET>` query param

Set `CRON_SECRET` env var in Vercel via CLI.

## Key Decisions
- **Compare completed weeks, not partial** — even if the cron fires Friday, you'd be comparing 5 days to 7 days. Full-week-to-full-week is the only meaningful comparison.
- **Dual auth scheme** — Vercel cron uses Bearer token header; manual/backfill uses query param. Both paths now authenticated.
- **Backfill limited to 8 weeks** — daily data has 30-day TTL, so older weeks can't be reconstructed from daily data. The stale weekly aggregates for those are the best we have.

## Testing & Validation
- Deployed to Vercel via push to main
- Ran backfill via curl — 4 weeks re-aggregated successfully
- Triggered fresh report via POST — confirmed corrected stats (396 vs 460 = -14%)

## Outcomes
