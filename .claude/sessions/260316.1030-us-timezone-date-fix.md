## Context
Support ticket from Kirstin Muraski (kirstin@kirstinmuraski.com) — when she entered 3/18 for a calendar event, all calendar buttons showed 3/17. She confirmed the date was consistently shifted back by one day.

Previously, we had fixed timezone issues for users AHEAD of UTC (Brisbane, UAE) by converting UTC timestamps to the target timezone to recover the intended date. This fix broke for US users (BEHIND UTC) when Kit sends midnight-UTC timestamps.

## Objectives
1. Fix the off-by-one date bug for US/western timezone users
2. Ensure the fix doesn't break the existing Brisbane/UAE timezone handling
3. Commit uncommitted local changes (stateless ICS migration)

## Implementation Details
Kit's date picker has two behaviors:
- **Mode A (midnight-local-as-UTC)**: Sends midnight in the user's browser TZ encoded as UTC (e.g., Brisbane user picking Feb 5 sends "2026-02-04T14:00:00.000Z")
- **Mode B (midnight-UTC)**: Sends the date as midnight UTC (e.g., "2026-03-18T00:00:00.000Z") or as a date-only string ("2026-03-18")

The fix detects which mode by checking if the UTC time is midnight:
- Midnight UTC or date-only → use the UTC date directly (it IS the intended date)
- Non-midnight UTC → timezone conversion path (preserves Brisbane/UAE fix)

This is mathematically safe because midnight-local-as-UTC can only equal midnight-UTC when the user is at UTC+0, where the conversion is an identity operation anyway.

## Key Decisions
- Chose midnight-UTC detection over a flag/config approach — handles both Kit behaviors automatically
- Removed Vercel KV dependency from test endpoint since ICS serving is now stateless
- Added 3 targeted regression tests rather than broad test expansion
