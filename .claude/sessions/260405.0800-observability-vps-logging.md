## Context
All 4 bugs in project history were caught by user reports, never by internal monitoring. The session goal was to build observability so future issues are detected proactively or diagnosed faster when users do report them.

Also resolved a pending bug: Ballantyne (Paige Brunton team) reported Apple Calendar returning 500 error. Root cause was double `decodeURIComponent()` in ICS endpoint crashing on `%` characters in event descriptions. Fixed and replied.

## Objectives
1. Fix Apple Calendar 500 error (Ballantyne report)
2. Build corpus logging for all Kit API requests
3. Add schema monitor to detect Kit payload changes
4. Add VPS health check running real calendar scenarios
5. Add CI gate for integration tests
6. Solve the log retention problem (Vercel's 1-hour ephemeral buffer)

## Implementation Details

### Apple Calendar Fix
`api/ics/index.js` was calling `decodeURIComponent()` on query params that were already decoded by the runtime. Double-decode crashes on any `%` in event descriptions (e.g. "50% off"). Removed the redundant decode calls.

### Corpus Logging
`corpusLog()` function in `api/calendar-block/index.js` fires on every request with:
- `event: "calendar_block_request"` — raw Kit input, detected mode, resolved date
- `event: "calendar_block_error"` — exception details on failure path
- `event: "kit_schema_change"` — when Kit sends unknown payload keys

### BetterStack → VPS
Initially wired BetterStack via `@logtail/node` SDK (Vercel Hobby plan doesn't support log drains). Free tier has 3-day retention. After discussion, decided VPS-based logging was sufficient — eliminated the third-party dependency and closed the BetterStack account.

### VPS Log Receiver
- Python HTTP server (`/home/claude/kit-calendar-log-receiver/receiver.py`)
- Listens on port 9201, Bearer token auth
- Appends JSONL to daily files: `corpus-YYYY-MM-DD.jsonl`
- PM2 process `kit-log-receiver`, persisted across reboots
- UFW opened for port 9201
- Vercel env vars: `VPS_LOG_URL`, `VPS_LOG_SECRET`

### VPS Health Check
- `scripts/vps-health-check.py` deployed to `/home/claude/kit-calendar-health/health_check.py`
- Tests 4 scenarios: Brisbane (Mode A), Eastern (Mode B), Dubai (Mode A), generic US
- Actually fetches the ICS file, not just checking HTTP status
- Cron: Friday 7pm UTC
- Fires Slack alert on failure

### CI Gate
`.github/workflows/integration-tests.yml` — runs HTTP integration tests on every push to main. Uses `VERCEL_TOKEN` secret for SHA-bound deployment URL testing.

### Schema Monitor
Detects when Kit sends payload keys not in `KNOWN_SETTINGS_KEYS`. Fires Slack `kit_schema_change` alert. Scope limited to key additions (not removal or encoding drift).

## Key Decisions

**VPS over BetterStack**: BetterStack's free tier has 3-day retention — exactly the window that would miss retroactive forensics when users report bugs 4+ days later. Self-hosted VPS receiver is free, unlimited retention, and already accessible via SSH. No meaningful downside for this use case.

**Dual-write → VPS-only**: Started with dual-write (BetterStack + VPS) to get UI querying. After discussion, decided jq/grep on JSONL files is sufficient for the debugging scenarios this project actually faces. Simplified to VPS-only and closed BetterStack account.

**Fire-and-forget logging**: `corpusLog()` uses `.catch(() => {})` — logging failures never affect the calendar link generation. User experience is never degraded by observability infrastructure.

**Mode B boundary tolerance**: Investigated whether sub-second jitter (`00:00:00.500Z`) would break midnight-UTC detection. Confirmed safe (second is still 0). Second-level jitter would break it, but Kit constructs Mode B dates from Rails `Date.new()` which always produces `.000Z`. Documented and moved on.
