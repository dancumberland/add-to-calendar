## Context
Sharon Ma from Wordfetti Group reported two issues:
1. Brisbane timezone was missing from dropdown (had to use Sydney which has DST)
2. Dates were off by one day when adding events to Google Calendar

This was traced to a fundamental issue: Kit's date picker sends "midnight in browser timezone" as UTC, causing date extraction to fail for timezones ahead of UTC.

## Objectives
1. Fix the Brisbane date-off-by-one bug

## Implementation Details

### Root Cause Analysis
JavaScript's `Date` object cannot represent "just a date" - it always represents a specific instant. When Kit's date picker sends a date:
- Brisbane user selects Feb 5
- Browser creates: Feb 5 00:00 Brisbane (GMT+10)
- Kit sends as UTC: `2026-02-04T14:00:00.000Z`
- Old code extracted: `2026-02-04` (wrong!)

### Fix Applied
```javascript
// OLD (broken for eastern timezones):
const datePart = dateISO.split('T')[0];

// NEW (works for all timezones):
const utcMoment = DateTime.fromISO(dateISO, { zone: 'utc' });
const dateInTargetTz = utcMoment.setZone(ianaTimezone);
const datePart = dateInTargetTz.toISODate();
```

## Key Decisions

1. **Use UTC for calendar URLs**: Research confirmed UTC with Z suffix is the gold standard for Google, Outlook, and ICS compatibility

2. **Convert to target timezone before extracting date**: This handles both eastern (ahead of UTC) and western (behind UTC) timezones correctly

3. **Analytics use UTC consistently**: Server-side analytics should use UTC for global consistency; user timezone stored as metadata for breakdowns

4. **Curated timezone list vs full IANA**: 70+ carefully selected zones cover 99%+ of users while keeping UI manageable
